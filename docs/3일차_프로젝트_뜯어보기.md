# 3일차 - 프로젝트 뜯어보기
 
## 1. 디렉터리는 어떤 역할을 수행하며, 작성해야 할 파일의 내용
 
FastAPI 프로젝트를 "라우터(APIs) - 서비스(Services) - 저장소(Repositories) - 데이터베이스(Models)"로 계층을 나누는 이유는, 각 계층이 하나의 책임만 갖게 해서 코드 변경의 영향 범위를 좁히고, 테스트와 유지보수를 쉽게 만들기 위해서다. 요청이 들어와서 응답이 나가기까지 데이터가 어느 계층을 거치는지 순서대로 정리하면 이렇다.
 
```
클라이언트 요청
   ↓
apis/      (라우터: 요청을 받아 schemas로 검증)
   ↓
services/  (비즈니스 로직: 검증된 데이터로 실제 처리)
   ↓
repositories/ (DB 접근: 실제 쿼리 실행)
   ↓
models/    (SQLAlchemy ORM: 테이블과 매핑)
   ↓
DB
```
 

### app/core/

프로젝트 전역에서 공통으로 쓰는 설정과 인프라 코드를 모아두는 곳이다. 비즈니스 로직이 아니라 "프로젝트가 돌아가기 위한 기반 설정"을 담당한다.

- `config.py`: `.env`에 저장된 환경변수(DB 접속 정보, SECRET_KEY 등)를 읽어와 애플리케이션 전역에서 쓸 수 있는 설정 객체로 만든다.
- `db/databases.py`: SQLAlchemy 엔진 생성, 세션(Session) 관리, DB 커넥션을 다른 계층에 주입(Dependency Injection)하는 코드를 담는다.
- `db/models.py` 또는 `models/` 상위의 `Base`: 모든 ORM 모델이 상속받는 `Base` 클래스(`declarative_base()`)를 정의해서, 이후 만들어질 모델들이 공통 기반을 갖게 한다.

여기 있는 코드는 회원, 게시글, 상품 등 어떤 도메인이든 상관없이 프로젝트 전체가 공유하는 부분이라서, 특정 기능(회원가입, 상세조회 등)과 관련된 로직은 여기 두지 않는다.

### app/models/

SQLAlchemy ORM 모델, 즉 파이썬 클래스로 DB 테이블 구조를 정의하는 곳이다. 테이블의 컬럼, 타입, 제약조건(PK, FK, unique 등), 테이블 간 관계(`relationship`)를 클래스 형태로 작성한다.

```python
from sqlalchemy import Column, Integer, String
from app.core.db.databases import Base

class User(Base):
    __tablename__ = "users"

    id = Column(Integer, primary_key=True, index=True)
    name = Column(String(10), nullable=False)
    email = Column(String(30), unique=True, nullable=False)
    password = Column(String(255), nullable=False)
```

여기서 만든 클래스는 곧 실제 DB 테이블과 1:1로 매핑되고, 이후 alembic이 이 클래스를 보고 마이그레이션 파일을 자동 생성해준다.

### app/repositories/

DB에 직접 접근하는 코드(쿼리)를 모아두는 계층이다. `session.query(...)`, `session.add(...)`, `session.commit()` 같은 SQLAlchemy 세션 조작이 여기서만 일어나도록 격리한다.

```python
from sqlalchemy.orm import Session
from app.models.user import User

class UserRepository:
    def __init__(self, db: Session):
        self.db = db

    def get_by_id(self, user_id: int) -> User | None:
        return self.db.query(User).filter(User.id == user_id).first()

    def create(self, user: User) -> User:
        self.db.add(user)
        self.db.commit()
        self.db.refresh(user)
        return user
```

이렇게 분리해두면 나중에 DB를 바꾸거나 쿼리 방식을 바꿀 때 이 파일들만 수정하면 되고, 서비스 로직이나 API 코드는 건드릴 필요가 없어진다.

> 참고: 현재 프로젝트 템플릿에는 `app/repositories/` 폴더가 비어있는 상태라 git에는 보이지 않는다 (git은 빈 폴더를 추적하지 않기 때문). 실제 개발 시 이 폴더 안에 파일을 만들면서 채워나가야 한다.

### app/schemas/

Pydantic `BaseModel`을 상속한 클래스를 정의하는 곳이다. `models/`가 "DB에 어떻게 저장되는가"를 정의한다면, `schemas/`는 "API가 요청/응답으로 어떤 형태의 데이터를 주고받는가"를 정의한다.

```python
from pydantic import BaseModel

class UserRegisterRequest(BaseModel):
    name: str
    age: int
    email: str
    password: str

class UserResponse(BaseModel):
    id: int
    name: str
    age: int
    email: str

    class Config:
        from_attributes = True  # SQLAlchemy 객체를 그대로 응답으로 변환 가능
```

같은 "회원"을 다루더라도 요청용(`Request`), 응답용(`Response`), DB 저장용(`Create`) 스키마를 목적에 따라 따로 만드는 게 일반적이다. 예를 들어 응답 스키마에는 `password` 필드를 아예 넣지 않아서, 비밀번호가 API 응답으로 노출되는 걸 원천적으로 막을 수 있다.

### app/services/

실제 비즈니스 규칙(도메인 로직)을 처리하는 계층이다. "이메일 중복이면 안 된다", "비밀번호는 해시해서 저장한다" 같은 판단과 절차가 여기 들어간다. `repositories/`를 호출해서 DB 작업을 위임하고, 여러 repository의 결과를 조합하는 것도 이 계층의 역할이다.

```python
from app.repositories.user_repository import UserRepository
from app.schemas.user import UserRegisterRequest

class UserService:
    def __init__(self, repository: UserRepository):
        self.repository = repository

    def register(self, body: UserRegisterRequest):
        existing = self.repository.get_by_email(body.email)
        if existing:
            raise ValueError("이미 사용 중인 이메일입니다.")
        # 비밀번호 해시 등 비즈니스 규칙 처리
        return self.repository.create(...)
```

### app/apis/

HTTP 요청을 직접 받는 라우터(엔드포인트) 코드를 담는다. `APIRouter()`로 라우터 객체를 만들고, `@router.get`, `@router.post` 등으로 경로와 메서드를 지정한다. 이 계층의 역할은 최소한으로 유지하는 게 좋다. 즉, 요청을 `schemas`로 검증하고, `services`를 호출해서 결과를 받아 응답 스키마로 반환하는 "중개자" 역할만 한다.

```python
from fastapi import APIRouter, Depends
from app.schemas.user import UserRegisterRequest, UserResponse
from app.services.user_service import UserService

router = APIRouter(prefix="/practice_api")

@router.post("/users", response_model=UserResponse)
def register_user(body: UserRegisterRequest, service: UserService = Depends()):
    return service.register(body)
```

## 2. 각 파일의 역할

### 2.1 `app/main.py`

FastAPI 애플리케이션의 시작점(Entry Point)이다.

현재 코드의 역할은 다음과 같다.

- `app = FastAPI()`로 애플리케이션 인스턴스 생성
- `practice_router`를 애플리케이션에 등록
- 프로젝트 루트 경로인 `BASE_DIR` 계산
- `static`, `media` 디렉터리가 없으면 생성
- `/static`, `/media` 경로에 정적·업로드 파일 디렉터리 마운트
- `/healthcheck`에서 서버 상태 확인
- `/`에서 `static/index.html` 반환
- 정의되지 않은 프런트엔드 경로를 `index.html`로 연결하는 SPA용 catch-all 라우트 제공

서버는 프로젝트 루트에서 다음과 같이 실행할 수 있다.

```bash
uv run uvicorn app.main:app --reload
```

FastAPI 자동 API 문서는 기본적으로 다음 주소에서 확인한다.

- Swagger UI: `http://127.0.0.1:8000/docs`
- ReDoc: `http://127.0.0.1:8000/redoc`

> 현재 `main.py`에는 `practice_router` import와 `app.include_router(practice_router)`가 각각 두 번 작성되어 있다. 문서 과제와 별개로 추후 중복 코드를 한 번씩만 남기는 것이 좋다.

### 2.2 `app/core/config.py`

`pydantic-settings`의 `BaseSettings`를 이용해 환경설정을 읽는다.

- `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME`을 정의한다.
- 프로젝트 루트의 `.env` 값을 읽는다.
- `.env`에 정의되지 않은 값은 클래스에 작성된 기본값을 사용한다.
- `extra="ignore"`로 Settings에 정의되지 않은 추가 환경변수는 무시한다.
- 파일 마지막의 `settings = Settings()`를 다른 모듈에서 import하여 사용한다.

실제 비밀번호가 들어 있는 `.env`는 Git에 올리지 않는다. 저장소의 `.env.example`을 복사하여 로컬에서 `.env`를 생성한다.

```bash
cp .env.example .env
```

Windows PowerShell에서는 다음 명령을 사용할 수 있다.

```powershell
Copy-Item .env.example .env
```

### 2.3 `pyproject.toml`

Python 프로젝트의 기본 정보와 직접 사용하는 의존성을 선언하는 파일이다.

현재 설정에는 다음 내용이 포함되어 있다.

- 프로젝트명: `ai-health-web-assignment`
- 버전: `0.1.0`
- Python 요구 버전: `3.13` 이상
- 주요 패키지
  - `fastapi[standard]`: FastAPI와 표준 실행 도구
  - `sqlalchemy[asyncio]`: 비동기 ORM
  - `asyncmy`: 비동기 MySQL 드라이버
  - `alembic`: DB 마이그레이션
  - `pydantic-settings`: 환경변수 설정 관리
  - `uuid6`: UUID v7 생성
  - `cryptography`: 암호화 관련 기능 지원

새 패키지는 파일을 직접 편집하기보다 다음 명령으로 추가하는 것이 안전하다.

```bash
uv add 패키지명
```

### 2.4 `uv.lock`

프로젝트에 설치되는 모든 패키지의 **정확한 버전과 의존 관계**를 고정하는 lock 파일이다.

`pyproject.toml`이 프로젝트가 직접 요구하는 패키지와 허용 버전 범위를 적는 파일이라면, `uv.lock`은 그 조건을 계산한 실제 설치 결과를 기록한다. 팀원이 `uv sync`를 실행하면 동일한 의존성 환경을 재현할 수 있다.

```bash
uv sync
```

`uv.lock`은 자동 생성 파일이므로 보통 직접 수정하지 않는다. 의존성 추가·삭제 후 uv가 변경한 lock 파일은 `pyproject.toml`과 함께 Git에 커밋한다.

## 3. 데이터베이스 연결 설정: `app/core/db/databases.py`

이 프로젝트는 MySQL과 비동기로 통신하도록 구성되어 있다.

### 3.1 연결 URL 생성

```python
DATABASE_PREFIX = "mysql+asyncmy://"
DATABASE_URI = f"{settings.DB_USER}:{settings.DB_PASSWORD}@{settings.DB_HOST}:{settings.DB_PORT}/{settings.DB_NAME}"
DATABASE_URL = f"{DATABASE_PREFIX}{DATABASE_URI}"
```

`.env`에서 읽은 설정을 다음 형식의 SQLAlchemy URL로 조합한다.

```text
mysql+asyncmy://사용자:비밀번호@호스트:포트/데이터베이스명
```

### 3.2 비동기 엔진 생성

```python
async_engine = create_async_engine(DATABASE_URL, echo=False, future=True)
```

엔진은 SQLAlchemy와 DB 사이의 연결을 관리한다. `echo=False`이므로 실행 SQL을 콘솔에 출력하지 않는다. 개발 중 쿼리 확인이 필요할 때만 일시적으로 `True`를 고려할 수 있다.

### 3.3 세션 팩토리 생성

```python
AsyncSessionLocal = async_sessionmaker(
    bind=async_engine,
    autoflush=False,
    expire_on_commit=False,
)
```

`AsyncSessionLocal`은 요청마다 사용할 비동기 세션을 만드는 팩토리이다. 세션은 조회, 추가, 수정, 삭제와 트랜잭션을 처리한다.

### 3.4 선언적 Base 생성

```python
Base = declarative_base()
```

각 SQLAlchemy 모델은 `Base`를 상속한다. Alembic은 `Base.metadata`를 읽어 모델과 실제 DB 스키마의 차이를 찾는다.

### 3.5 FastAPI에 DB 세션 주입

```python
async def async_get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as db:
        yield db
```

`async with` 블록이 끝날 때 세션이 닫히므로 요청마다 안전하게 세션을 만들고 정리할 수 있다. API에서는 다음처럼 주입할 수 있다.

```python
from typing import Annotated

from fastapi import Depends
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.db.databases import async_get_db


@router.get("/users")
async def get_users(
    db: Annotated[AsyncSession, Depends(async_get_db)],
):
    ...
```

`async_get_db()`는 세션을 제공하고 닫는 역할만 한다. 성공 시 `commit`, 실패 시 `rollback`을 어느 계층에서 담당할지는 팀 내에서 한 가지 방식으로 통일해야 한다.

## 4. SQLAlchemy 모델 & Alembic 마이그레이션

**왜 필요한가**
지금까지 회원 데이터를 파이썬 리스트로 다뤘는데, 이는 서버 재시작 시 사라지는 임시 데이터다. 실제 서비스는 데이터베이스(DB)에 저장해야 하고, 그 테이블 구조를 파이썬 코드로 표현한 것이 **SQLAlchemy 모델**이다.

**SQLAlchemy란**
파이썬에서 DB를 다루게 해주는 ORM(Object-Relational Mapping) 라이브러리. 테이블을 클래스로, 행(row)을 객체로 다뤄서 SQL을 직접 안 써도 조회·추가·수정·삭제가 가능하다. 다만 모델 작성만으로는 실제 DB가 바뀌지 않는다 — 어디까지나 설계도일 뿐이다.

**Alembic이란**
모델(설계도) 변경사항을 실제 DB에 반영해주는 마이그레이션 도구. Git이 코드 변경 이력을 남기듯, Alembic은 DB 구조 변경 이력을 파일로 남겨 추적·롤백이 가능하게 해준다.

**마이그레이션 흐름**
1. 모델 작성/수정
2. 마이그레이션 파일 자동 생성 (변경사항 감지)
3. 생성된 파일 검토
4. 실제 DB에 적용
5. 필요시 이전 버전으로 되돌리기

## 5. API 구현 흐름 (레이어드 아키텍처)

**왜 계층을 나누는가**
데이터·로직·라우팅을 한 파일에 몰아 쓰면 프로젝트가 커질수록 관리가 어려워진다. 그래서 역할별로 폴더를 나누는 레이어드 아키텍처를 쓴다.

**계층별 역할**

| 계층 | 역할 |
|---|---|
| apis | URL과 함수를 연결하는 라우팅만 담당 |
| schemas | 요청/응답 데이터 형식 정의 (예: 응답 필드 제한) |
| services | 비즈니스 로직·판단 (예: 없으면 404) |
| repositories | DB 접근 (조회·저장·수정·삭제) |
| models | SQLAlchemy 테이블 구조 |

**요청 처리 순서**
클라이언트 → apis(라우팅) → schemas(형식 검증) → services(판단) → repositories(DB 접근) → models(테이블) → 응답 반환

**나누는 이유**
- 역할이 명확해 유지보수·협업이 쉬움
- 각 계층을 독립적으로 테스트 가능
- 팀원끼리 계층별로 분업 가능
