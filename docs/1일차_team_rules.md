# 팀 협업 규칙

## 1. 기본 원칙

* 팀원 모두가 다함께 참여한다.⭐
* 맡은 업무와 진행 상황을 팀원에게 투명하게 공유한다.
* 일정 변경이나 문제가 발생하면 혼자 해결하려고 미루지 않고 바로 알린다.
* 의견이 다를 때는 사람보다 문제와 근거에 집중한다.
* 다른 팀원의 코드를 수정해야 할 경우 먼저 해당 팀원과 상의한다.

## 2. 역할 및 업무 분담

* 업무를 시작하기 전에 담당자와 완료 목표를 정한다.
* 하나의 업무에는 가급적 한 명의 담당자를 지정한다.
* 담당자는 업무 진행 상황과 결과를 팀원에게 공유한다.
* 업무가 지연될 것으로 예상되면 가능한 한 빠르게 알리고 일정을 다시 조정한다.

## 3. Git 브랜치 규칙

* `main` 브랜치는 항상 실행 가능한 상태로 유지한다.
* 기능 개발이나 수정 작업은 개인 브랜치에서 진행한다.
* 브랜치 이름은 영문 소문자와 하이픈을 사용한다.

브랜치 이름 예시:

```text
feature/login
feature/user-profile
fix/login-error
docs/team-rules
```

브랜치 종류:

* `feature/기능명`: 새로운 기능 개발
* `fix/수정내용`: 오류 수정
* `docs/문서명`: 문서 작성 및 수정
* `refactor/대상`: 기능 변경 없는 코드 개선

## 4. Commit 규칙

* 하나의 커밋에는 하나의 작업 내용만 포함한다.
* 커밋 메시지만 보고 변경 내용을 이해할 수 있도록 작성한다.
* 작업 중인 파일 전체를 무조건 커밋하지 않고 변경 파일을 확인한다.

커밋 메시지 형식:

```text
타입: 작업 내용
```

사용할 타입:

* `feat`: 새로운 기능 추가
* `fix`: 오류 수정
* `docs`: 문서 작성 및 수정
* `style`: 코드 형식 및 디자인 수정
* `refactor`: 코드 구조 개선
* `test`: 테스트 코드 작성 및 수정
* `chore`: 설정 및 기타 작업

커밋 메시지 예시:

```text
feat: 회원가입 기능 추가
fix: 로그인 실패 오류 수정
docs: 팀 협업 규칙 작성
style: 메인 화면 레이아웃 수정
```

## 5. Push 및 Pull Request 규칙

* 작업을 시작하기 전에 원격 저장소의 최신 내용을 받는다.
* `main` 브랜치에 직접 기능 코드를 push하지 않는다.
* 개인 브랜치에서 작업한 뒤 Pull Request를 생성한다.
* Pull Request에는 작업 내용과 확인이 필요한 사항을 작성한다.
* 최소 한 명의 팀원이 코드를 확인한 후 `main` 브랜치에 병합한다.
* 충돌이 발생하면 관련 코드를 작성한 팀원과 상의하여 해결한다.
* 병합이 완료된 브랜치는 필요하면 삭제한다.

## 6. 코드 작성 규칙

* 변수명과 함수명은 역할을 이해할 수 있도록 작성한다.
* 같은 의미의 이름과 표현 방식을 일관되게 사용한다.
* 불필요하게 중복되는 코드를 작성하지 않는다.
* 복잡한 로직에는 필요한 경우 간단한 주석을 작성한다.
* 사용하지 않는 코드와 테스트용 출력문은 정리한 후 제출한다.

## 7. 보안 규칙

* 비밀번호, API 키, 토큰 등 민감한 정보는 GitHub에 올리지 않는다.
* 실제 환경변수 파일인 `.env`는 커밋하지 않는다.
* 환경변수의 항목만 안내하는 `.env.example` 파일을 사용한다.
* 민감한 정보가 실수로 올라간 경우 즉시 팀원에게 알리고 해당 정보를 폐기하거나 재발급한다.

## 8. 소통 규칙

* 주요 결정 사항은 모든 팀원이 확인할 수 있는 채널에 기록한다.
* 팀 메시지를 확인하면 가능한 한 당일 안에 응답한다.
* 긴급한 문제나 일정 지연은 발견 즉시 공유한다.
* 회의가 끝나면 결정 사항, 담당자, 마감일을 간단히 정리한다.
* 부득이하게 회의에 참석하지 못하면 사전에 알린다.

## 9. 일정 및 완료 기준

* 담당 업무에는 가능한 한 마감일을 지정한다.
* 기능이 정상적으로 실행되는지 직접 확인한 후 완료로 표시한다.
* 오류가 남아 있거나 추가 작업이 필요한 경우 이를 명확하게 공유한다.
* 제출 전에는 전체 기능, 문서, 보안 정보 포함 여부를 함께 점검한다.

## 10. 문제 해결 원칙

* 오류가 발생하면 실행 환경, 오류 메시지, 재현 방법을 함께 공유한다.
* 팀원 간 의견이 다를 경우 프로젝트 목표, 사용자 요구사항, 일정과 기술적 근거를 기준으로 결정한다.
* 합의가 어려운 경우 팀장이 의견을 정리하여 최종 결정을 내린다.
* 규칙은 프로젝트 진행 상황과 팀원 합의에 따라 수정할 수 있다.
