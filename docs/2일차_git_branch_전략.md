## Git Branch 전략이 필요한 이유

여러 명이 동시에 같은 코드베이스를 건드리면 서로의 작업이 충돌하거나 덮어써질 위험이 있다. 브랜치를 나눠서 작업하면 각자 독립된 공간에서 개발하고, 완성된 부분만 골라서 합칠 수 있다. 브랜치 전략은 이 "언제 브랜치를 만들고 언제 합칠지"에 대한 팀 차원의 규칙이다. 대표적으로 Git Flow와 GitHub Flow 두 가지가 있다.

---

## Git Flow

Vincent Driessen이 제안한 브랜치 전략. 브랜치를 용도별로 세분화해서 개발 프로세스를 구조화한다.

### 브랜치 종류

- **main(master)**: 제품의 배포 가능한 최종 상태를 저장하는 브랜치
- **develop**: 개발 중인 기능을 통합하는 브랜치
- **feature/**: 새로운 기능 개발을 위한 브랜치
- **release/**: 배포 준비를 위한 브랜치
- **hotfix/**: 운영 중인 서비스의 긴급 수정 사항을 처리하는 브랜치

### 개발 흐름

1. 신규 기능 개발 시 `develop`을 기준으로 `feature` 브랜치를 딴다.
2. 작업이 끝난 `feature` 브랜치는 PR을 통해 리뷰받은 후 `develop`으로 merge한다.
3. 다음 출시 버전을 위해 `develop`에서 `release` 브랜치를 따서 배포 준비(테스트, 버그 수정)를 진행한다.
4. `release` 브랜치가 충분히 검증되면 `main`으로 merge해서 배포하고, 동시에 `develop`에도 merge한다.
5. 배포 이후 발견된 긴급 버그는 `main`에서 `hotfix` 브랜치를 따서 수정하고, 완료되면 `main`과 `develop` 양쪽에 반영한다.

```bash
git checkout develop
git pull origin develop
git checkout -b feature/login develop
```

### 특징

- 브랜치 종류가 많아서 구조가 복잡하지만, 배포 버전 관리와 긴급 수정 대응이 명확하게 나뉜다.
- 배포 주기가 정해져 있고 규모가 큰 프로젝트, QA 단계가 필요한 서비스에 적합하다.

## GitHub Flow

Git Flow보다 훨씬 단순한 전략. 브랜치를 최소한으로 유지한다.

### 브랜치 종류

- **main(master)**: 기본 브랜치. 언제든 배포 가능한 상태를 유지한다.
- **feature/**: 기능 추가나 수정을 위한 브랜치. main에서 바로 분기한다.

### 개발 흐름

1. `main`에서 `feature` 브랜치를 딴다.
2. 기능 개발이 끝나면 PR을 올리고 리뷰를 받는다.
3. 리뷰가 승인되면 바로 `main`으로 merge한다.
4. merge된 내용을 즉시(혹은 빠르게) 배포한다.

### 특징

- `develop`, `release` 브랜치가 없어서 구조가 단순하고 브랜치 관리 부담이 적다.
- merge와 배포 주기가 짧아서 지속적 배포(CI/CD)를 하는 팀에 적합하다.
- 배포 준비 단계가 따로 없기 때문에, merge 전 테스트와 리뷰가 충분히 이뤄져야 안정성이 확보된다.

## Git Flow vs GitHub Flow 비교

| 구분 | Git Flow | GitHub Flow |
|---|---|---|
| 브랜치 종류 | main, develop, feature, release, hotfix | main, feature |
| 구조 | 복잡함 | 단순함 |
| 배포 주기 | 버전 단위로 정기 배포 | 수시로 빠르게 배포 |
| 적합한 프로젝트 | 규모가 크고 QA/릴리즈 절차가 있는 프로젝트 | 소규모 팀, 지속적 배포(CI/CD) 프로젝트 |
| merge 대상 | feature → develop, release → main | feature → main |

## 우리 팀의 선택

- 선택한 전략: GitHub Flow
- 선택 이유: 짧은 실습 프로젝트라 브랜치 구조를 복잡하게 나눌 필요가 없어서 GitHub Flow를 선택했다. main 브랜치와 feature 브랜치만으로 간단하게 작업하고, PR 리뷰 후 바로 merge하는 방식이 이번 과제 규모에 적합하다고 판단했다.
- 브랜치 명명 규칙: 
1. 소문자만 사용하고, 단어 사이는 하이픈(-)으로 구분한다. 
2. 나중에 버그 수정 브랜치가 필요해지면 fix/버그내용 형식으로 구분한다.
3. main 브랜치에 직접 push하지 않는다.
4. 기능 하나당 하나의 브랜치를 사용한다.
5. commit 메시지에는 변경 목적을 명확히 적는다.
6. PR은 본인이 아닌 다른 팀원이 검토한다.
- 리뷰 규칙: 
1. PR은 본인이 아닌 다른 팀원이 검토한다.
2. 요구사항대로 동작하는지 직접 테스트해보고 Approve한다.
3. 수정이 필요하면 Request changes로 남기고 반영 후 재검토한다.
